# Dooray MCP Server 구현 계획

작성 기준일은 2026-08-06이다.

이 계획은 기존 PR 두 건을 먼저 처리한 뒤 신규 계획 15개를 브랜치와 PR 단위로 나눈다.
각 계획은 독립 검토와 되돌리기가 가능해야 한다.

## 선행 게이트

열린 PR은 새 구현에 흡수하지 않고 작성자 이력을 보존해 먼저 처리한다.

| 순서 | 대상 | 처리 방침 |
| ---: | --- | --- |
| 1 | PR #27 숫자 프로젝트 ID 통과 | 이슈 #26의 직접 해결로 검증하고 병합한다. |
| 2 | PR #28 위키 페이지 댓글 목록 | `legacy` 20번째 도구로 보존하고 병합한다. |

두 PR이 병합된 뒤 신규 계획 브랜치를 최신 `main`에서 갱신한다.

## 병렬 경계

계획 3이 중앙 확장점을 만든 뒤에만 병렬 작업을 시작한다.

가능한 병렬 묶음은 다음과 같다.

- 계획 6, 9, 11, 12는 계획 5 뒤 병렬 시작이 가능하다.
- 계획 7과 8은 계획 6 뒤 병렬 시작이 가능하다.
- 계획 10은 계획 9 뒤 시작한다.
- 계획 13은 삭제 대상 도메인이 모두 준비된 뒤 시작한다.

공유 문서는 동시에 수정하지 않는다.
각 계획은 문서 소유 파일을 명확히 나누고, 기능 대응표 갱신은 병합 순서에 맞춰 한 브랜치에서만 처리한다.

## 계획 2 추가 범위

계획 2는 의존성 보안 갱신과 같은 기반 작업으로 CI 실행 환경도 점검한다.
PR #27 실행 `31073945476`과 PR #28 실행 `31074355359`에서 `actions/setup-java@v4` 폐기 경고와 Node.js 20 기반 action 강제 호환 경고가 확인됐다.
계획 2에서 공식 문서와 당시 실행 로그를 다시 확인해 실제 갱신 버전을 결정한다.

계획 2는 다음을 포함한다.

- 공식 GitHub Actions 문서와 각 action 릴리스 노트로 최신 호환 버전을 확인한다.
- `.github/workflows/*.yml`의 action 버전을 갱신한다.
- Java 21, Gradle 8.13, Kotlin 2.4.10 조합이 CI에서 그대로 동작하는지 검증한다.
- 경고 해소 여부를 PR 본문에 실측 로그로 기록한다.

기능 구현이나 도구 계약 변경은 계획 2 범위에 넣지 않는다.

## 계획 9 이슈 #2 범위

이슈 #2는 루트 페이지에서 시작해 depth별 DFS를 여러 도구 호출로 반복하는 흐름이 느린 문제다.
계획 9는 이를 `dooray_wiki`의 `operation=tree`로 해결한다.

`tree` operation은 다음 계약을 가진다.

- 한 번의 호출로 대상 위키의 페이지 목록을 필요한 만큼 가져온다.
- API가 평탄 목록을 반환하면 `parent` 관계로 서버 안에서 트리를 구성한다.
- `root_page_id`가 있으면 해당 루트를 기준으로 하위 트리만 반환한다.
- `max_depth`가 있으면 지정 깊이까지만 반환한다.
- 쪽매김이 필요한 API이면 서버가 전체 페이지를 순회하되 상한과 시간 제한을 적용한다.
- 캐시가 유효하면 반복 호출에서 페이지 목록을 재사용한다.
- 결과에는 캐시 사용 여부, 조회한 페이지 수, 잘린 노드 수, 다음 조정 힌트를 포함한다.

계획 9의 시험은 다음을 포함한다.

- parent 관계가 섞인 평탄 목록에서 안정적인 트리를 만드는 단위 시험
- 루트 제한 시험
- depth 제한 시험
- 전체 페이지 처리 시험
- 캐시 적중과 만료 시험
- 이전 방식처럼 여러 tool call을 반복하지 않아도 같은 트리를 얻는 회귀 시험

이 계획이 병합되면 이슈 #2는 새 구현 PR로 해결된 것으로 연결한다.

## 기본 검증 묶음

모든 코드 계획은 다음 검증을 실행한다.

```bash
git diff --check
CI=true ./gradlew clean build --no-daemon --console=plain
./gradlew testMcpIntegration --no-daemon --console=plain
```

자격 증명이 필요한 Dooray 실제 통합 시험은 별도 게이트로 둔다.
실제 삭제 API와 외부 사용자에게 영향을 주는 시험은 자동으로 실행하지 않는다.

## 계획별 중단 조건

각 계획은 다음 중 하나에 해당하면 중단하고 상위 계획을 갱신한다.

- 독립 구현 원칙을 지키려면 제품 범위 변경이 필요하다.
- Dooray 공식 API가 요구 기능을 제공하지 않아 추정 보완이 필요한 상황이다.
- 자격 증명이나 외부 게시 권한 없이는 검증을 완료할 수 없다.
- 삭제, 배포, 릴리스처럼 되돌릴 수 없는 외부 작업이 필요하다.
